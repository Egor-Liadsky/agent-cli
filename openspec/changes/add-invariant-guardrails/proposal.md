## Why

Сейчас поведение агента ограничивают только промпт пользователя и системный
промпт чата — оба живут в диалоге и оба может переписать сообщение
пользователя или неудачный system prompt. Архитектурные решения проекта
(единственный трейт `Agent`, разделение `agentcore`/`agentcli`, фиксированный
порядок стадий `pipeline.rs`) и бизнес-правила (например, ключ провайдера
принадлежит `agentd`, а не клиенту) нигде не проверяются на уровне ответа
модели: агент может предложить решение, которое их нарушает, просто потому
что пользователь попросил. Нужен набор инвариантов, которые хранятся отдельно
от истории чата, явно попадают в рассуждения модели и проверяются механически,
а не только упоминанием в системном промпте.

## What Changes

- Новый модуль `invariants` в `agentcore`: типы инварианта (`id`, `statement`,
  `category`, необязательный `rationale`) и реестр `InvariantSet`, загружаемый
  из файла конфигурации (`invariants.toml`), а не из истории сообщений или
  `ChatSettings` чата.
- Инварианты внедряются в каждый запрос как отдельный блок системного
  контекста конвейера (не часть пользовательской истории), чтобы модель
  явно их видела при рассуждении.
- Новая выходная политика `pipeline::InvariantGuard` (`OutputPolicy`):
  проверяет ответ модели на явное нарушение зарегистрированных инвариантов
  через отдельный служебный вызов агента (аналогично `Judge`, но с бинарным
  вердиктом «нарушение/нет») и отклоняет ответ (`PolicyOutcome::Reject`) с
  кодом `invariant_violation` и человекочитаемой причиной, называющей
  нарушенный инвариант.
- При отказе агент не предлагает альтернативную реализацию сам: он
  возвращает отказ с объяснением, какой инвариант противоречит просьбе, и
  (если применимо) какой инвариант позволил бы решить задачу иначе.
- `agentcli`: команда `agentcli config invariants` — просмотр активных
  инвариантов (источник конфигурации, не чат).
- `agentd`: инварианты читаются из `AGENTD_INVARIANTS_PATH`
  (по умолчанию не заданы — политика по умолчанию пропускает всё, как
  `AllowAllOutput`), сам список в тело запроса не передаётся и клиентом не
  переопределяется.

## Capabilities

### New Capabilities
- `invariant-guardrails`: хранение инвариантов отдельно от диалога,
  внедрение их в контекст рассуждения агента и принудительная проверка
  ответа выходной политикой конвейера с объяснимым отказом при конфликте.

### Modified Capabilities
(нет — существующих capability-спек в `openspec/specs/` ещё нет)

## Impact

- `agent-cli/crates/core`: новый модуль `invariants.rs`, регистрация
  `InvariantGuard` в списке выходных политик, изменение `RequestContext`
  (добавление ссылки на активный `InvariantSet`), новые тесты в
  `pipeline.rs`/`invariants.rs`.
- `agent-cli/crates/cli`: новая подкоманда `config invariants`, чтение пути
  к файлу инвариантов из конфигурации CLI.
- `agent-sever`: чтение `AGENTD_INVARIANTS_PATH`, отказ на явную попытку
  передать инварианты в теле запроса (аналогично уже существующему отказу
  на клиентский `api_key`), README обоих репозиториев — новая переменная
  окружения и команда.
- Формат файла `invariants.toml` и его местоположение по умолчанию.
