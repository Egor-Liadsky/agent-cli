## Context

Мотивация — в `proposal.md` («Why»), требования — в `specs/client-transport` и
`specs/client-config`.

Сейчас единственная реализация трейта `Agent` — `HttpAgent` в
`crates/core/src/agent/http.rs`. Она совмещает две роли: собирает запрос
Chat Completions для облачного провайдера и диспетчеризует запрос в
`agent/ollama.rs`, если у чата провайдер `Ollama`. Этим типом пользуются и
консольный клиент, и сервис `agentd`, который подключает `agentcore`
git-зависимостью с ветки `main`, а локально подменяет её секцией `[patch]` в
`agent-sever/.cargo/config.toml`.

Контракт `/v1/chat` у сервиса уже есть и меняться не должен: запрос —
`{messages, settings, metadata}`, успешный ответ — `{request_id, content,
reasoning, model, usage, timing, policy}`, ошибка — `{"error": {code, message,
request_id}}` плюс заголовок `x-request-id`. Тело с полем `api_key` на любом
уровне вложенности отклоняется кодом `400`.

## Goals / Non-Goals

**Goals:**

- Запрет прямого вызова облачного провайдера из клиента держится графом
  зависимостей: нужного кода нет в дереве `agentcli`.
- Разделение крейтов выполняется механически, отдельным шагом от изменения
  поведения клиента, чтобы регрессию было легко локализовать.
- Контракт `/v1` и поведение сервиса не меняются: для `agentd` это перенос
  кода провайдера в отдельный крейт.

**Non-Goals:**

- Стриминг ответа, хранение истории чатов на сервере, выдача токенов и квоты.
- Изменение логики конвейера на сервисе и состава стадий.
- Автоматическая правка пользовательского конфига: устаревшие поля только
  вызывают предупреждение.

## Decisions

### Разделение по крейтам, а не по модулям одного крейта

Запрет должен проверять компилятор. Модульная граница внутри `agentcore` этого
не даёт: любой публичный модуль ядра доступен и клиенту. Поэтому облачный код
выносится в отдельный крейт `agentupstream`, которого нет в зависимостях
`agentcli`. Альтернатива — cargo-фичи (`agentcore/upstream`) — отвергнута:
фичи в workspace объединяются, и включение фичи сервисом вернуло бы облачный
код в сборку клиента.

### `agentcore` сохраняет Ollama и трейт `Agent`

Ollama остаётся в ядре, потому что им пользуются оба потребителя: клиент —
как прямым путём, сервис — как одним из провайдеров. Из `HttpAgent` в ядре
остаётся общая часть, нужная обоим: сборка системного промпта из стратегии
рассуждения и формата ответа, выбор модели по настройкам чата,
`AgentError`, `ExchangeLog`. Публичная реализация `Agent` для локальных
моделей (условно `OllamaAgent`) выделяется из нынешней диспетчеризации, потому
что после разделения «одного типа на оба провайдера» больше нет.

### Диспетчеризация по `Provider` переезжает к потребителям

Выбор между агентами делает вызывающая сторона: клиент — между `ServerAgent`
и локальным агентом, сервис — между `agentupstream` и локальным агентом. Это
и есть механизм запрета: у клиента в списке вариантов физически нет облачного.

### `ServerAgent` реализует существующий трейт `Agent`

Так TUI, разовый вопрос и конвейер логирования остаются нетронутыми: меняется
только то, какой объект подставляется. Поля `usage`/`timing` ответа
раскладываются в `MessageMeta`, поэтому строка телеметрии работает без правок.
Модель из ответа сервиса возвращается наверх и показывается вместо
запрошенной.

### Расширение `AgentError` под коды сервиса

Существующие варианты (`Timeout`, `Provider`, `Transport`, `Decode`,
`MissingApiKey`) не покрывают отказ политики `422` и неизвестный токен `401`, а
`request_id` в них негде хранить. `AgentError` дополняется вариантами для этих
случаев (в том числе заменой смысла `MissingApiKey` на «токен клиента не
задан или неизвестен») и полем `request_id`. Разбор ошибки идёт по коду
состояния HTTP, а `code` из тела используется в тексте: коды состояния
задокументированы контрактом, поэтому опираться на них надёжнее.

### Тесты клиента против `wiremock`

Сервис — обычный HTTP, поэтому `ServerAgent` тестируется тем же способом, что
и сервис: `wiremock` в dev-зависимостях `agentclient`. Это единственная новая
зависимость.

### Порядок изменений в двух репозиториях

Правки ядра доезжают до сервиса только через `main` репозитория `agent-cli`.
Поэтому шаг с переводом `agent-sever` на `agentupstream` идёт после того, как
разделение крейтов запушено: сначала `[patch]` на два крейта для локальной
сборки, затем проверка без `[patch]` через `cargo generate-lockfile` и
`cargo test --locked`.

## Risks / Trade-offs

- Клиент без запущенного `agentd` теряет облачные чаты → в README обоих
  репозиториев описывается порядок запуска «сначала сервис, потом клиент», а
  недоступность адреса даёт понятную ошибку с адресом, а не транспортный шум.
- Пользовательские ключи остаются лежать в старых конфигах → однократное
  предупреждение при чтении устаревших полей; молча файл не переписываем,
  чтобы не терять чужие правки.
- Два крейта в git-зависимостях `agent-sever` расходятся по коммитам, если
  запушить не всё → в лок-файле проверяется, что оба крейта указывают на один
  коммит (`grep -A2 'name = "agentcore"' Cargo.lock` и то же для
  `agentupstream`).
- Разделение `HttpAgent` затрагивает и путь Ollama, который в задачу изменения
  поведения не входит → шаг 1 выполняется механически и заканчивается зелёными
  `cargo build` и `cargo test`, до любых правок поведения.
- Двойное логирование обмена: клиент пишет свой JSONL, сервис — свой → на
  стороне клиента журналируется обмен с сервисом, а не с провайдером; это
  ожидаемо и отражается в README.

## Migration Plan

1. Разделение крейтов без изменения поведения (клиент временно ходит в облако
   через `agentupstream`).
2. `ServerAgent` с тестами.
3. Переключение клиента на `ServerAgent` и снятие зависимости на
   `agentupstream`.
4. Конфигурация клиента: `server_url`, `client_token`, команды, TUI, чтение
   устаревшего конфига.
5. Push `agent-cli/main`, перевод `agent-sever` на `agentupstream`, обновление
   `[patch]` и лок-файла.
6. README обоих репозиториев.

Откат до шага 5 — обычный revert в `agent-cli`: сервис продолжает собираться
против прежнего коммита `main`, пока лок-файл не обновлён.
