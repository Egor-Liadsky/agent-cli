## Context

См. `proposal.md` — Why. Ключевое ограничение: `agentcore::ChatSettings` —
общий тип ядра, используемый и клиентом, и `agent-sever` (через git-
зависимость). Сервис сознательно не хранит `max_context_tokens` в
`ChatSettings` (design.md изменения `limit-context-window` в `agent-sever`:
«лимит — это ограничение транспортного уровня... `agentcore` не должен
знать о HTTP-контракте `agentd`»), и не применяет клиентское значение
`ChatSettingsDto.max_context_tokens` при `PATCH /v1/chats/{id}` — оно
работает только при `POST /v1/chat`, на один запрос. У клиента, в свою
очередь, нет собственного хранилища чатов (`specs/client-chat-storage`,
`agent-cli/openspec/changes/drop-client-chat-storage`): список, история и
настройки чата целиком живут в сервисе, локально ничего не сохраняется.
Из этих двух фактов вместе следует, что персистентного «лимита контекста
конкретного чата» в текущей архитектуре не существует — только
клиентский умолчательный лимит, отправляемый на каждый запрос.

Тело `POST /v1/chat` собирает `ServerAgent::build_body`
(`crates/client/src/lib.rs:294`) в `ChatSettingsPayload`, куда уже попадают
поля, не входящие в `agentcore::ChatSettings` (`provider` — константа
`"cloud"` вместо `settings.provider`). Модель по умолчанию устроена так же:
`ServerAgent` хранит свой `model: String`, заданный в `CliAgent::from_config`
(`crates/cli/src/agent.rs:25`) из `Config.model`, и подставляет его, если у
чата модель не задана (`model_for`, `crates/client/src/lib.rs:74`).
`max_context_tokens` встраивается по тому же образцу.

## Goals / Non-Goals

**Goals:**
- Один настраиваемый клиентский лимит контекста, отправляемый в каждом
  `POST /v1/chat` (`ask` и `ask_in_chat`), без дублирования кода сборки
  тела запроса.
- Настройка равноправно доступна командой (`agentcli config context-limit`)
  и в TUI, по образцу уже существующих клиентских настроек подключения
  (`server_url`, `client_token`, `ollama_url`).

**Non-Goals:**
- Лимит контекста отдельного чата — недостижимо без изменения контракта
  `agent-sever` (см. Context); не предмет этого изменения.
- Валидация значения относительно операторского лимита сервиса — её делает
  `agentd` (`400 context_limit_invalid`/`context_limit_exceeded`), клиент
  лишь передаёт значение и показывает ответ сервиса.
- Изменение `agentcore::ChatSettings` — поле туда сознательно не
  добавляется (см. Decisions).

## Decisions

- **Хранить в `Config`, а не в `ChatSettings`.** `ChatSettings` — общий тип
  ядра, сериализуемый и в сохранённые настройки чата на сервере; добавление
  туда `max_context_tokens` создало бы поле, которое `agent-sever`
  де-факто не использует (сервис намеренно не переносит его в постоянные
  настройки чата — см. Context), и клиент был бы вынужден имитировать
  персистентность, которой на сервере нет. `Config` — уже место для
  клиентских умолчаний уровня «одно значение на все чаты» (`model`,
  `provider`, `sampling`), точно та же семантика.
  Альтернатива — добавить поле в `ChatSettings` и полагаться на то, что
  `PATCH /v1/chats/{id}` его сохранит: отклонено, потому что `agent-sever`
  сейчас игнорирует `ChatSettingsDto.max_context_tokens` вне разового
  `POST /v1/chat` (см. Context) — значение сохранённым не будет, а
  API будет создавать иллюзию персистентности там, где её нет.
- **`ServerAgent` получает значение конструктором, как `model`.** Тот же
  путь, что уже есть для модели по умолчанию: `Config` → `CliAgent::from_config`
  → `ServerAgent::new` → `ChatSettingsPayload` в `build_body`. Не требует
  протаскивать новое поле через `ChatSettings`/трейт `Agent`.
- **Поле показывается в разделе «Подключение» TUI, а не «Сэмплинг».**
  Семантически это не параметр сэмплирования модели, а настройка
  транспортного уровня — как `server_url`/`client_token`/`ollama_url`,
  общая для всех чатов. Сохраняется тем же путём (`save_connection`-подобная
  функция, апдейт `Config`, `Config::save()`), а не через
  `request_update_chat`, которым в TUI сохраняются настройки, реально
  персистентные на сервере (`provider`, `model`, `reasoning` и т.д.).
- **Отдельная подкоманда `config context-limit`, а не поле в `Sampling`.**
  `Sampling`/`Format` управляют параметрами `ChatSettings` по умолчанию для
  новых чатов; `context-limit` — клиентский параметр без аналога на
  сервере. Три действия (`set`/`clear`/`show`) по образцу существующих
  подкоманд `SamplingAction`, а не одно значение позиционным аргументом:
  так явно поддержан сброс лимита, аналогично `SamplingAction::Reset`.

## Risks / Trade-offs

- Один лимит на клиента, а не на чат → пользователю с чатами на разных
  моделях (разные реальные окна) придётся использовать самый тесный лимит
  для всех сразу либо часто его менять. Принято как компромисс: точная
  настройка на чат потребовала бы отдельного изменения контракта
  `agent-sever` (см. Non-Goals).
- Значение не валидируется клиентом при вводе относительно фактического
  окна модели — только формат (положительное целое). Реальную проверку
  всё равно делает `agentd`; дублировать её здесь excessive для клиента без
  доступа к операторскому лимиту сервиса.
