## Context

Мотивация — в `proposal.md` («Why»). Текущее состояние: один бинарный крейт
`agentcli` (`Cargo.toml`, `src/`), внутри него `src/agent/` (трейт `Agent`,
`HttpAgent`, Ollama) и `src/config.rs` (`Config`, `ChatSettings`). Ограничения,
которые формируют решение:

- CLI и TUI (`src/tui.rs`, 2163 строки) должны продолжать работать без
  изменений в поведении, поэтому ядро переносится механически, а правки
  ограничиваются импортами и явной передачей параметров логирования.
- Пользователь выбрал размещение сервиса в **отдельном репозитории**
  `/Users/egor_lyadskiy/ai/agent-sever`, поэтому ядро должно стать
  библиотекой, публикуемой наружу этого репозитория.
- Репозиторий `agent-cli` публичный
  (`https://github.com/Egor-Liadsky/agent-cli`) — git-зависимость на него
  не требует секретов при сборке образа.
- OpenSpec-артефакты живут в `agent-cli/openspec/`, а часть реализации
  делается в другом каталоге; это отступление от `allowedEditRoots`
  зафиксировано осознанно.

## Goals / Non-Goals

**Goals:**

- Ядро (`agentcore`) собирается и тестируется независимо от терминала.
- Стадии конвейера подключаются списком, а не правкой обработчика.
- Сервер отличает таймаут провайдера от ошибки провайдера, не разбирая строки.
- Сборка образа не требует доступа к рабочей машине разработчика.

**Non-Goals:**

- Публикация `agentcore` на crates.io. Достаточно git-зависимости.
- Общий workspace на два репозитория (cargo этого не поддерживает без
  единого корня).
- Абстракция над HTTP-фреймворком: `axum` используется напрямую.

## Decisions

### Решение 1: два репозитория, ядро подключается git-зависимостью

`agent-cli` становится workspace из `crates/core` (библиотека `agentcore`) и
`crates/cli` (бинарник `agentcli`). `agent-sever` — отдельный репозиторий
с крейтом `agentd`, зависящим от `agentcore` так:

```toml
agentcore = { git = "https://github.com/Egor-Liadsky/agent-cli", branch = "main" }
```

Локальная разработка против неопубликованного ядра идёт через
`.cargo/config.toml` в `agent-sever` (в `.gitignore`):

```toml
[patch."https://github.com/Egor-Liadsky/agent-cli"]
agentcore = { path = "../agent-cli/crates/core" }
```

*Альтернативы.* Path-зависимость `../agent-cli/crates/core` в `Cargo.toml`:
проще, но ломает сборку образа — путь выходит за пределы build context, и
пришлось бы делать контекстом родительский каталог. Vendoring ядра копией
в `agent-sever`: развязывает репозитории, но заводит второй источник правды
для кода, который меняется в обоих задачах. Git-зависимость с
локальным `[patch]` даёт и воспроизводимую сборку образа, и удобную
разработку; цена — ядро надо запушить в `main` до сборки образа.

### Решение 2: типизированная ошибка ядра рядом с `anyhow`

Сервису нужно различать таймаут (504), ошибку провайдера (502) и ошибку
конфигурации, а разбирать текст сообщения нельзя. Трейт остаётся
`async fn ask(...) -> anyhow::Result<AgentReply>`, но ядро возвращает
`anyhow::Error`, построенную из типизированного `AgentError`
(`Timeout`, `Provider { status, message }`, `Transport`, `MissingApiKey`,
`Decode`). Сервер делает `err.downcast_ref::<AgentError>()` и отображает
в код ответа; CLI ничего не замечает и продолжает печатать
`{err:#}`.

*Альтернативы.* Смена типа результата трейта на `Result<AgentReply, AgentError>`
чище, но переписывает все места вызова в TUI и CLI и нарушает требование
«перенос механический». Возврат к разбору строк отвергнут: коды ответов
сервиса зависели бы от текста сообщения провайдера.

### Решение 3: логирование обмена — свой неблокирующий писатель, без новых зависимостей

`logs_dir()` на `CARGO_MANIFEST_DIR` заменяется на явную конфигурацию:

```rust
pub struct ExchangeLog { /* канал в фоновый поток-писатель */ }
impl ExchangeLog { pub fn disabled() -> Self; pub fn to_dir(dir: PathBuf) -> Self; }
```

Внутри — `std::sync::mpsc::Sender<LogLine>` и выделенный поток, открывающий
файлы `requests.jsonl` / `responses.jsonl` на дозапись. `HttpAgent` держит
`Arc<ExchangeLog>` и только отправляет строку в канал, поэтому запись не
блокирует асинхронный путь. Отключённый лог — вариант, в котором отправка
ничего не делает и директория не создаётся.

*Альтернативы.* `tracing-appender::non_blocking` решает ту же задачу, но
добавляет зависимость сверх согласованного списка и тянет `tracing` в ядро,
которому оно больше нигде не нужно. `tokio::task::spawn_blocking` на каждую
запись — лишние задачи в рантайме и зависимость ядра от наличия рантайма
tokio у вызывающей стороны.

### Решение 4: путь логов CLI

CLI перестаёт писать в `<репозиторий>/logs` (после разделения на крейты этот
путь указывал бы на `crates/cli/logs`) и пишет в
`dirs::data_dir()/agentcli/logs`, с переопределением переменной
`AGENTCLI_LOG_DIR`. Это единственное наблюдаемое изменение в CLI, и оно
касается отладочного артефакта, а не команд, вывода или конфига.

*Альтернатива.* Сохранить `logs/` рядом с текущим рабочим каталогом —
засоряет любой каталог, из которого запущен установленный бинарник.

### Решение 5: конвейер владеет агентом через `Arc<dyn Agent>`

```rust
pub struct Pipeline {
    agent: Arc<dyn Agent>,
    input: Vec<Arc<dyn InputPolicy>>,
    output: Vec<Arc<dyn OutputPolicy>>,
    judge: Option<Arc<dyn Judge>>,
}
pub enum PolicyOutcome {
    Pass,
    Rewrite(PolicyPayload),          // изменённая история или изменённый ответ
    Reject { code: String, reason: String },
}
```

`RequestContext` несёт `request_id`, `history`, `settings`, `client_id` и
накопленный `PolicyLog` (результаты стадий). Ошибка стадии
(`Result::Err`) и отказ стадии (`PolicyOutcome::Reject`) — разные исходы:
первый даёт 500/502 на транспорте, второй — 422. Результат конвейера —
`PipelineOutcome::{ Completed { reply, policy }, Rejected { stage, code, reason, policy } }`.

Возврат «изменённой полезной нагрузки» отдельным вариантом (а не мутацией
контекста на месте) выбран потому, что делает изменение явным для журнала
стадий и не даёт политике незаметно поменять чужие поля контекста.

Задел на стриминг: конвейер оперирует целым `AgentReply`, но `Pipeline`
не встроен в обработчик и в дальнейшем может получить второй метод
для потокового прохода; контракт `POST /v1/chat` не запрещает добавить
`stream: true` и отдельный тип ответа.

### Решение 6: конфигурация сервиса и белый список моделей

`AgentdConfig::from_env()` читает переменные `AGENTD_*`, плюс `PORT` как
запасной источник адреса прослушивания. Пустой `AGENTD_ALLOWED_MODELS`
означает «разрешена только `AGENTD_MODEL`», а не «разрешено всё»: иначе
клиент мог бы направить трафик на произвольную модель провайдера. Отсутствие
`AGENTD_UPSTREAM_API_KEY` — ошибка на старте (`std::process::exit(1)` после
сообщения), а не на первом запросе.

`settings.provider = "ollama"` разрешён только если задан `AGENTD_OLLAMA_URL`;
иначе 400.

### Решение 7: `request_id` — UUID v4

Существующий `request_id()` в ядре («секунды-наносекунды») достаточен для
локальных JSONL-логов, но не годится как публичный идентификатор запроса
нескольких реплик. Сервис использует `uuid` (feature `v4`). Это единственная
зависимость сверх списка из задания; альтернатива — счётчик плюс метка
времени — даёт коллизии между репликами и хуже читается в логах хостинга.

### Решение 8: слои и порядок middleware

Снаружи внутрь: `TraceLayer` (tracing) → присвоение `request_id` и заголовка
`x-request-id` → `RequestBodyLimitLayer` (413) → `ConcurrencyLimitLayer` +
`LoadShedLayer` (429) → `TimeoutLayer` (общий таймаут) → аутентификация
(только на `/v1`) → обработчик. Проверка токена стоит после лимитов,
чтобы дешёвые отказы не требовали разбора тела, и внутри слоя
`request_id`, чтобы 401 тоже нёс идентификатор.

Таймаут провайдера задаётся отдельно, на `reqwest::Client` внутри
`HttpAgent`, и даёт `AgentError::Timeout` → 504; общий `TimeoutLayer`
страхует зависание в стадиях конвейера.

## Risks / Trade-offs

- **Ядро и сервис расходятся во времени: образ собирается из `main`, а разработка
  идёт под локальным `[patch]`** → в задачах реализации зафиксирован шаг
  «запушить ядро перед первой сборкой образа»; CI сервиса собирает без
  `[patch]`, поэтому расхождение обнаруживается сразу.
- **Git-зависимость привязывает сервис к ветке `main` чужого репозитория**
  → в `Cargo.lock` фиксируется коммит, обновление зависимости становится
  явным шагом (`cargo update -p agentcore`).
- **Механический перенос 4238 строк может незаметно поменять поведение TUI**
  → перенос выполняется отдельным шагом с зелёной сборкой и ручной проверкой
  `agentcli ask` и `agentcli chat` до того, как начнётся работа над сервисом.
- **Смена пути логов CLI** → задокументирована в README и переопределяется
  переменной `AGENTCLI_LOG_DIR`.
- **Пустой список клиентских токенов означает открытый сервис** → поведение
  соответствует заданию, но README и лог старта явно предупреждают, что
  аутентификация выключена.
- **`ConcurrencyLimitLayer` без `LoadShedLayer` не отказывает, а ставит в
  очередь** → используются оба слоя вместе, иначе требование «429 при
  превышении конкурентности» не выполняется.
- **Отказ от смены типа результата `Agent::ask`** → сервер обязан помнить про
  `downcast`; если ядро когда-нибудь потеряет типизированную ошибку, сервис
  молча начнёт отвечать 502 вместо 504. Покрывается тестом на таймаут.

## Migration Plan

1. Workspace и перенос ядра в `agent-cli`, зелёная сборка, ручная проверка
   `ask` и `chat`. Откат — один коммит.
2. Правки ядра (лог, типизированная ошибка, конвейер) с юнит-тестами.
   Ядро остаётся обратно совместимым для CLI.
3. Пуш `agent-cli/main` — после этого ядро доступно сервису по git.
4. Новый репозиторий `agent-sever`: скелет, `/healthz`, затем `/v1/chat`,
   затем конвейер, конфигурация и лимиты, затем тесты и образ.
5. Развёртывание — только образ сервиса; CLI распространяется как раньше,
   его откат независим.
