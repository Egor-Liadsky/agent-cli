## Purpose

Правила эксплуатации сервиса агента в контейнере: откуда берётся конфигурация,
как проверяются клиенты, какие действуют лимиты и таймауты, что попадает
в журнал и как процесс завершается. Эти правила отделяют сервис от состояния
консольного клиента и делают его пригодным для хостинга.

## ADDED Requirements

### Requirement: Конфигурация только из окружения

Сервис SHALL читать конфигурацию из переменных окружения и MUST NOT читать
пользовательский конфигурационный файл консольного клиента. Набор переменных
SHALL покрывать адрес прослушивания, клиентские токены, параметры провайдера
(базовый адрес, ключ, модель, провайдер, адрес Ollama), разрешённые модели,
таймаут запроса, предельный размер тела, предельную конкурентность, формат
и назначение журнала.

#### Scenario: Пользовательский конфигурационный файл присутствует

- **WHEN** на машине есть файл конфигурации консольного клиента с другими
  значениями
- **THEN** сервис его не читает и работает по значениям из окружения

#### Scenario: Адрес прослушивания по умолчанию

- **WHEN** адрес прослушивания не задан ни отдельной переменной, ни переменной
  порта, принятой на хостингах
- **THEN** сервис слушает `0.0.0.0:8080`

#### Scenario: Порт задан хостингом

- **WHEN** задана только переменная порта, принятая на хостингах
- **THEN** сервис слушает этот порт

### Requirement: Отсутствие ключа провайдера останавливает запуск

Если ключ провайдера не задан, сервис SHALL завершиться при запуске с понятной
ошибкой и MUST NOT принимать запросы, отказывая на первом обращении.

#### Scenario: Запуск без ключа

- **WHEN** сервис запускается без заданного ключа провайдера
- **THEN** процесс завершается с ненулевым кодом и сообщением о том, какая
  переменная окружения не задана

### Requirement: Аутентификация клиентов по токену

Сервис SHALL поддерживать список клиентских токенов. При непустом списке
каждый запрос к эндпоинтам `/v1` SHALL требовать заголовок `Authorization`
со схемой `Bearer` и токеном из списка. Сравнение токенов SHALL выполняться
за постоянное время. При пустом списке сервис SHALL стартовать и обслуживать
запросы без проверки.

#### Scenario: Запрос без токена при заданном списке

- **WHEN** список токенов не пуст, а запрос приходит без заголовка `Authorization`
- **THEN** сервис отвечает кодом 401

#### Scenario: Запрос с неверным токеном

- **WHEN** предъявленный токен отсутствует в списке
- **THEN** сервис отвечает кодом 401, а вызов модели не выполняется

#### Scenario: Служебные эндпоинты без токена

- **WHEN** запрашивается `/healthz` без заголовка `Authorization`
- **THEN** сервис отвечает кодом 200

### Requirement: Лимиты запроса

Сервис SHALL ограничивать размер тела запроса и число одновременно
обрабатываемых запросов настраиваемыми значениями. Превышение размера тела
SHALL давать код 413, превышение допустимой нагрузки — код 429.

#### Scenario: Слишком большое тело

- **WHEN** клиент отправляет тело больше заданного предела
- **THEN** сервис отвечает кодом 413 и не передаёт содержимое модели

#### Scenario: Превышена конкурентность

- **WHEN** число одновременных запросов превышает заданный предел
- **THEN** избыточные запросы получают код 429

### Requirement: Таймауты обработки

Сервис SHALL применять таймаут к вызову провайдера и общий таймаут обработки
запроса. Истечение таймаута провайдера SHALL давать код 504 и SHALL освобождать
занятые ресурсы обработки.

#### Scenario: Провайдер отвечает слишком долго

- **WHEN** провайдер не отвечает в пределах заданного таймаута
- **THEN** сервис отвечает кодом 504, а обработка запроса прекращается

### Requirement: Структурированный журнал без содержимого диалога

Сервис SHALL вести структурированный журнал с выбором формата: JSON или текст.
Для каждого запроса журнал SHALL содержать идентификатор запроса,
идентификатор клиента, модель, длительность, код ответа и токены.
Сервис MUST NOT записывать тексты промптов и ответов по умолчанию; такая
запись SHALL включаться отдельным признаком конфигурации.

#### Scenario: Журнал в продовой конфигурации

- **WHEN** сервис работает с форматом журнала JSON и без включённой записи
  содержимого
- **THEN** каждая запись о запросе содержит идентификатор запроса, клиента,
  модель, длительность, код ответа и токены и не содержит текста промпта
  и ответа

#### Scenario: Запись содержимого включена явно

- **WHEN** признак записи содержимого диалога включён
- **THEN** тексты промпта и ответа попадают в журнал

#### Scenario: Ключ провайдера в журнале

- **WHEN** сервис пишет диагностическую запись о своей конфигурации
- **THEN** ключ провайдера отображается маскированным и не встречается
  в журнале целиком

### Requirement: Сервис не хранит состояние диалога

Сервис SHALL обрабатывать каждый запрос по присланной клиентом истории и
MUST NOT сохранять историю между запросами.

#### Scenario: Два независимых запроса

- **WHEN** клиент присылает два запроса подряд без общей истории в теле
- **THEN** второй запрос обрабатывается без учёта содержимого первого

### Requirement: Корректное завершение процесса

Сервис SHALL завершаться по сигналам `SIGTERM` и `SIGINT`, прекращая приём
новых соединений и дожидаясь завершения уже принятых запросов в пределах
отведённого времени.

#### Scenario: Остановка под нагрузкой

- **WHEN** процесс получает `SIGTERM` во время обработки запроса
- **THEN** новые соединения не принимаются, активный запрос доводится
  до ответа, и только после этого процесс завершается

### Requirement: Поставка в виде контейнера

Сервис SHALL собираться в образ контейнера, в котором рантайм не содержит
инструментов сборки. Образ SHALL слушать порт из переменной окружения и
SHALL объявлять проверку состояния по `/healthz`.

#### Scenario: Запуск образа

- **WHEN** образ запускается с заданными переменной порта и ключом провайдера
- **THEN** сервис принимает запросы на этом порту, а проверка состояния
  образа отвечает успешно

### Requirement: Клиент переиспользует соединения провайдера

Сервис SHALL создавать клиент провайдера один раз при старте и переиспользовать
его между запросами. Сервис MUST NOT создавать нового агента на каждый
входящий запрос.

#### Scenario: Серия запросов подряд

- **WHEN** сервис обрабатывает несколько запросов подряд
- **THEN** все они выполняются одним и тем же экземпляром клиента провайдера
