## Purpose

Сетевой контракт сервиса агента: как клиент присылает промпт по HTTP, что
получает в ответ и как выражаются ошибки. Контракт версионирован и рассчитан
на то, что стадии контроля и потоковая отдача появятся позже без слома
существующих клиентов.

## ADDED Requirements

### Requirement: Запрос диалога по HTTP

Сервис SHALL принимать `POST /v1/chat` с телом в формате JSON. Тело SHALL
содержать ровно одно из полей `prompt` (строка) или `messages` (история
сообщений); `prompt` SHALL быть эквивалентен истории из одного пользовательского
сообщения. Поле `settings` необязательно и накладывается поверх серверных
значений по умолчанию. Поле `metadata` необязательно и не влияет на вызов
модели.

#### Scenario: Запрос с полем prompt

- **WHEN** клиент отправляет тело с непустым `prompt` и без `messages`
- **THEN** сервис обрабатывает запрос как историю из одного пользовательского
  сообщения и отвечает кодом 200

#### Scenario: Запрос с полем messages

- **WHEN** клиент отправляет тело с непустым массивом `messages` и без `prompt`
- **THEN** сервис передаёт эту историю модели и отвечает кодом 200

#### Scenario: Заданы оба поля

- **WHEN** тело содержит и `prompt`, и `messages`
- **THEN** сервис отвечает кодом 400 и кодом ошибки `invalid_request`

#### Scenario: Не задано ни одного поля

- **WHEN** тело не содержит ни `prompt`, ни `messages`, либо оба пусты
- **THEN** сервис отвечает кодом 400 и кодом ошибки `invalid_request`

#### Scenario: Настройки переопределяют значения по умолчанию

- **WHEN** тело содержит `settings` с частью полей
- **THEN** заданные поля переопределяют серверные значения по умолчанию,
  а незаданные берутся из конфигурации сервиса

### Requirement: Ключ провайдера принадлежит сервису

Сервис MUST NOT принимать ключ провайдера модели от клиента. Запрос, содержащий
поле `api_key` в любом месте тела, SHALL быть отклонён явной ошибкой, а не
обработан с игнорированием поля.

#### Scenario: Клиент прислал api_key

- **WHEN** тело запроса содержит поле `api_key`
- **THEN** сервис отвечает кодом 400 и кодом ошибки `invalid_request`,
  а вызов модели не выполняется

### Requirement: Ответ диалога

Успешный ответ `POST /v1/chat` SHALL иметь код 200 и содержать поля
`request_id`, `content`, `reasoning` (может быть null), `model` с фактически
использованной моделью, `usage` с токенами, `timing` с длительностью и метками
времени и `policy` с результатами стадий конвейера. Поле `policy` SHALL
присутствовать всегда, даже когда стадии ничего не вернули.

#### Scenario: Успешный ответ модели

- **WHEN** провайдер успешно отвечает на запрос
- **THEN** клиент получает код 200, текст ответа в `content`, фактическую
  модель в `model`, заполненные `usage` и `timing` и объект `policy`
  с пустыми списками входных и выходных результатов и `judge` равным null

#### Scenario: Провайдер не вернул рассуждение

- **WHEN** провайдер не прислал цепочку рассуждений
- **THEN** поле `reasoning` в ответе равно null, а остальные поля заполнены

### Requirement: Ограничение выбора модели

Сервис SHALL принимать `settings.model` только из списка моделей, разрешённых
его конфигурацией. Модель вне списка SHALL приводить к ошибке запроса,
а не к вызову провайдера.

#### Scenario: Разрешённая модель

- **WHEN** клиент указывает модель, входящую в разрешённый список
- **THEN** запрос выполняется этой моделью, и она возвращается в поле `model`

#### Scenario: Неизвестная модель

- **WHEN** клиент указывает модель вне разрешённого списка
- **THEN** сервис отвечает кодом 400 и кодом ошибки `invalid_request`,
  а провайдер не вызывается

### Requirement: Служебные эндпоинты

Сервис SHALL предоставлять `GET /healthz`, отвечающий кодом 200, пока процесс
жив, и MUST NOT обращаться при этом к внешним сервисам. Сервис SHALL
предоставлять `GET /readyz`, отвечающий кодом 200 при валидной конфигурации
и кодом 503 при невалидной. Сервис SHALL предоставлять `GET /v1/models`
со списком моделей, разрешённых конфигурацией.

#### Scenario: Проверка живости

- **WHEN** клиент запрашивает `/healthz` при недоступном провайдере
- **THEN** сервис отвечает кодом 200

#### Scenario: Проверка готовности при валидной конфигурации

- **WHEN** ключ провайдера задан и базовый адрес разбирается корректно
- **THEN** `/readyz` отвечает кодом 200

#### Scenario: Список моделей

- **WHEN** клиент запрашивает `/v1/models`
- **THEN** сервис возвращает разрешённые конфигурацией модели и не возвращает
  моделей вне этого списка

### Requirement: Единый конверт ошибок

Любой ответ об ошибке SHALL иметь тело вида
`{"error": {"code": ..., "message": ..., "request_id": ...}}`.
Коды состояния SHALL соответствовать причинам: 400 — невалидный запрос;
401 — отсутствующий или неверный клиентский токен; 413 — превышен лимит тела;
422 — запрос отклонён политикой; 429 — сработал лимит сервиса либо провайдер
вернул ограничение частоты; 502 — провайдер вернул ошибку; 504 — таймаут
провайдера.

#### Scenario: Отказ входной политики

- **WHEN** входная политика отклоняет запрос
- **THEN** сервис отвечает кодом 422, а тело содержит код и причину отказа

#### Scenario: Ошибка провайдера

- **WHEN** провайдер отвечает ошибкой
- **THEN** сервис отвечает кодом 502 с конвертом ошибки

#### Scenario: Таймаут провайдера

- **WHEN** провайдер не отвечает в отведённое время
- **THEN** сервис отвечает кодом 504 с конвертом ошибки

### Requirement: Ошибки провайдера не проксируются дословно

Сообщение об ошибке, отдаваемое клиенту, MUST NOT содержать текст провайдера
дословно, внутренние адреса и ключи. Полный текст ошибки провайдера SHALL
записываться в журнал сервиса.

#### Scenario: Провайдер вернул подробную ошибку

- **WHEN** провайдер возвращает ошибку с внутренним адресом в тексте
- **THEN** клиент получает нормализованное сообщение без адреса и без ключа,
  а полный текст остаётся в журнале сервиса

### Requirement: Идентификатор запроса виден клиенту

Сервис SHALL присваивать каждому запросу идентификатор и возвращать его
в заголовке `x-request-id`, а также в теле успешного ответа и в теле ошибки.

#### Scenario: Идентификатор в успешном ответе

- **WHEN** запрос обработан успешно
- **THEN** значение `request_id` в теле совпадает со значением заголовка
  `x-request-id`

#### Scenario: Идентификатор в ошибке

- **WHEN** запрос отклонён с ошибкой
- **THEN** тело ошибки содержит тот же идентификатор, что и заголовок
  `x-request-id`
