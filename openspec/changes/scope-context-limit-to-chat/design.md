## Context

См. `proposal.md` — Why. Сейчас (`configure-max-context-tokens`)
`max_context_tokens` живёт только в `Config` и подставляется в каждый
запрос через отдельное поле `ServerAgent`, минуя `ChatSettings` — решение
было продиктовано тем, что `agent-sever` на тот момент нигде не хранил это
значение постоянно (`ChatSettingsDto.max_context_tokens` применялось только
к одному `POST /v1/chat`, `agent-sever/openspec/changes/limit-context-window`).
Одновременно уже существует параллельное изменение `agent-sever`,
`persist-chat-context-limit`, которое учит `ChatSettingsDto.apply_to` (и,
соответственно, хранилище чата) сохранять `max_context_tokens` в постоянных
настройках чата при `PATCH /v1/chats/{id}`, как уже сохраняются `model`,
`reasoning`, `thinking`, `experts`. Без этого хранения на стороне сервиса
поле в `ChatSettings` клиента было бы только косметическим: значение всё
равно терялось бы при следующей загрузке чата.

`agentcore::ChatSettings` — общий тип ядра (git-зависимость `agent-sever` →
`agent-cli`). Ядро сознательно не знает о HTTP-контракте `agentd`
(`crates/core` не зависит от терминала и от протокола), но уже несёт поля,
которые имеют смысл только в паре с сервисом (`model`, `reasoning`) — они
такие же настройки чата, как и лимит контекста, поэтому добавление сюда
`max_context_tokens` не нарушает эту границу: ядро остаётся не в курсе
деталей HTTP (кодов ошибок, имени поля в JSON), только хранит значение.

## Goals / Non-Goals

**Goals:**
- Лимит контекста — часть `ChatSettings`, сохраняется и загружается вместе
  с остальными настройками чата тем же путём, что `model`.
- `Config.max_context_tokens` остаётся, но как умолчание для новых чатов —
  по аналогии с `Config.model`/`effective_model`, без специального
  обращения при каждом запросе.
- Изменение синхронизировано с параллельным изменением `agent-sever`
  (`persist-chat-context-limit`): порядок раскатки описан в Migration Plan.

**Non-Goals:**
- Валидация значения относительно операторского лимита сервиса — как и
  прежде, на стороне `agentd`.
- Изменение формата ошибок `context_limit_invalid`/`context_limit_exceeded`
  — они уже показываются как обычная ошибка запроса, это не меняется.
- Собственно хранение на сервере (миграция БД, `ChatSettingsDto::apply_to`)
  — предмет `persist-chat-context-limit` в `agent-sever`, не этого
  изменения.

## Decisions

- **Поле переезжает в `ChatSettings`, `Config` становится умолчанием для
  новых чатов.** Тот же паттерн, что уже есть для `model`: `Config.model`
  не отправляется в запрос напрямую — он копируется в `ChatSettings.model`
  нового чата (`Config::default_chat_settings`), а `ServerAgent` при пустом
  `settings.model` дополнительно подставляет `Config.model` через
  `model_for` (двойная подстраховка: конфиг мог быть создан до появления
  поля в чате). Для лимита контекста вторая подстраховка не нужна: в
  отличие от модели, отсутствие лимита — не ошибка, а осмысленное состояние
  «лимит не сужен», поэтому `ServerAgent` просто берёт
  `settings.max_context_tokens` как есть, без обращения к `Config` в
  момент запроса.
- **`ServerAgent::new` теряет параметр `max_context_tokens`.** Он был нужен,
  когда значение было общим для клиента и не входило в `ChatSettings`;
  теперь оно приходит в каждом вызове `ask`/`ask_in_chat` вместе с
  `settings`, как и `model`, `reasoning`, `thinking` — специально хранить
  его в `ServerAgent` бессмысленно.
- **TUI: поле переезжает из раздела «Подключение» в поля, сохраняемые через
  `request_update_chat`.** Раздел «Подключение» в TUI объединяет как
  клиентские общие настройки (`server_url`, `client_token`, `ollama_url` —
  сохраняются в `Config` через `save_connection`), так и настройки текущего
  чата, показанные рядом для удобства (`provider`, `model` — сохраняются в
  `ChatSettings` через `request_update_chat`). Лимит контекста — из второй
  группы, как модель; он остаётся полем той же секции UI (менять
  расположение полей в панели — не предмет этого изменения), но код
  сохранения переезжает из `save_connection` в блок, формирующий
  `ChatSettings` для `request_update_chat`.
- **`PATCH /v1/chats/{id}` шлёт `max_context_tokens` всегда, включая
  `null`.** Как поля сэмплирования (`temperature`, `top_p`, ...) в
  `settings_payload`/`ChatSettingsUpdate` (`crates/client/src/chats.rs`) —
  не `skip_serializing_if`, а прямая сериализация `Option<u32>`, где `null`
  снимает значение. Требование спеки «пустое поле в TUI сбрасывает лимит
  чата» нельзя выполнить полем, которое при отсутствии значения просто не
  попадает в тело запроса: сервер не отличил бы «снять лимit» от «не
  трогать лимит». Симметрично `persist-chat-context-limit` в `agent-sever`
  должен разбирать это поле через тот же `double_option`, что уже применяют
  поля сэмплирования в `ChatSettingsDto`.
- **`config context-limit` остаётся, но означает умолчание.** Как
  `config set-model` не редактирует модель уже существующего чата, а только
  умолчание для новых, так и `config context-limit set/clear/show` теперь
  работает с `Config.max_context_tokens`. Редактирование лимита
  существующего чата — только через TUI (`Ctrl+P`), как и для модели: у
  клиента нет отдельной команды «изменить модель чата N» вне интерактивного
  режима, и для лимита контекста заводить её тоже не нужно.

## Risks / Trade-offs

- Клиент способен слать `ChatSettings.max_context_tokens` в
  `PATCH /v1/chats/{id}` раньше, чем `agent-sever` научится его сохранять
  (`persist-chat-context-limit` — отдельный change, может быть применено
  позже). Пока сервис не обновлён, поле в `PATCH` присутствует, но
  игнорируется (текущий контракт `ChatSettingsDto.max_context_tokens`
  применяется только к `POST /v1/chat`, PATCH его не знает) — значение,
  заданное в TUI, не переживёт перезапуск клиента, хотя в рамках одной
  открытой сессии `ChatSettings` в памяти клиента верно и запросы уходят с
  ним. Риск принят: совпадает с обычным порядком раскатки клиент/сервис в
  этом проекте (см. Migration Plan).
- Смена смысла `config context-limit` — с «действует на все чаты сейчас» на
  «умолчание для новых чатов» — меняет поведение команды без изменения её
  сигнатуры: пользователь, ожидающий прежнего эффекта (влияет на уже
  открытые чаты), должен будет вместо этого один раз поправить лимит в TUI
  для каждого нужного существующего чата. Смягчение — README документирует
  новую семантику явно.

## Migration Plan

1. Реализовать и запушить это изменение (`agent-cli`, ядро `agentcore`) в
   `main`: `ChatSettings.max_context_tokens` появляется в общем типе.
2. Реализовать `persist-chat-context-limit` в `agent-sever`: снять
   `[patch]` на время работы, `cargo generate-lockfile`, чтобы подтянуть
   новый `agentcore` из `main`, добавить хранение поля и миграцию БД,
   `cargo test --locked`.
3. До шага 2 включительно `PATCH /v1/chats/{id}` с `max_context_tokens`
   от уже обновлённого клиента сервисом безопасно игнорируется (см. Risks) —
   откатывать нечего, скоординированный релиз не блокирует независимую
   раскатку клиента и сервиса.
