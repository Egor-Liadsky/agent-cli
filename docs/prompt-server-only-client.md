# Промпт: консольный клиент ходит к облачной модели только через сервис `agentd`

## Роль и цель

Ты — Rust-инженер. В репозитории `agent-cli` (`/Users/egor_lyadskiy/ai/agent-cli`)
консольный клиент `agentcli` сейчас сам обращается к облачному провайдеру:
берёт `api_key` и `base_url` из пользовательского конфига и шлёт
`POST {base_url}/chat/completions`. Нужно это прекратить.

Целевое правило: **облачная модель доступна клиенту только через HTTP-сервис
`agentd`** (репозиторий `agent-sever`, `POST /v1/chat`). Ключ провайдера
принадлежит сервису, клиент его не знает и не хранит. Локальный Ollama —
единственное исключение: он остаётся прямым вызовом с машины пользователя,
потому что запросы туда никуда не уходят и ключа не требуют.

Запрет должен держаться компилятором, а не договорённостью: после изменения
крейт `agentcli` не должен иметь доступа к коду, который умеет звать облачного
провайдера напрямую.

## Что есть сейчас

- `crates/core` — библиотека `agentcore`: трейт `Agent`
  (`ask(&self, history: &[Message], settings: &ChatSettings) -> Result<AgentReply>`),
  типы `Message`/`Role`/`AgentReply`/`MessageMeta`, `config.rs`
  (`Config`, `ChatSettings`, `Provider::{Cloud, Ollama}`), `pipeline.rs`,
  `logging.rs` (JSONL-журнал обмена), `agent/error.rs` (`AgentError`).
- `crates/core/src/agent/http.rs` — `HttpAgent`: реализация `Agent`,
  которая для `Provider::Cloud` шлёт запрос в OpenAI-совместимый API, а для
  `Provider::Ollama` делегирует в `agent/ollama.rs`. Сейчас это единственная
  реализация `Agent`, и её используют и CLI, и сервис.
- `crates/cli` — бинарник `agentcli`: `cli.rs` (clap), `main.rs`, `tui.rs`,
  `chats.rs`. Конфиг лежит в `~/.config/agentcli/config.toml`, история чатов —
  в `~/.config/agentcli/chats/*.json`, параметры конкретного чата
  (`ChatSettings`) хранятся в файле чата.
- Репозиторий `agent-sever` подключает `agentcore` git-зависимостью с ветки
  `main` и уже реализует нужный контракт: `POST /v1/chat`, `GET /v1/models`,
  `GET /healthz`, `GET /readyz`, аутентификация по `Authorization: Bearer`,
  единый конверт ошибок и заголовок `x-request-id`.

## Целевая структура крейтов

Разложить workspace так, чтобы прямой вызов облачного провайдера был
недостижим из клиента:

- `crates/core` — `agentcore`, общая часть для клиента и сервиса: трейт
  `Agent` и типы, `config.rs`, `pipeline.rs`, `logging.rs`, `agent/error.rs`
  и **Ollama** (`agent/ollama.rs` вместе с публичной реализацией `Agent` для
  локальных моделей). Кода обращения к облачному провайдеру здесь больше нет.
- `crates/upstream` — новый крейт `agentupstream`: сюда переезжает облачная
  часть `HttpAgent` (сборка тела Chat Completions, ключ, `base_url`, разбор
  `usage` и `reasoning_content`). Зависит от `agentcore`. Потребитель ровно
  один — сервис `agentd`.
- `crates/client` — новый крейт `agentclient`: `ServerAgent` — реализация
  трейта `Agent` поверх `POST {server_url}/v1/chat`. Зависит от `agentcore`.
- `crates/cli` — `agentcli`: зависит от `agentcore` и `agentclient`.
  Зависимости на `agentupstream` у него нет и появиться не должно.

Текущий `HttpAgent` разделяется на две части: облачная уходит в
`agentupstream`, диспетчеризация по `Provider` перестаёт быть делом одного
типа. Клиент выбирает между `ServerAgent` и локальным Ollama-агентом, сервис —
между `agentupstream` и Ollama.

Переезд делать механически и отдельным шагом: сначала новые крейты и перенос
кода с зелёной сборкой и работающим CLI, только потом изменение поведения
клиента.

## Поведение клиента после изменения

`Provider::Cloud` в клиенте означает «через сервис `agentd`», а не «прямо в
облачный API». `Provider::Ollama` работает как сейчас — прямым запросом к
`{ollama_url}/api/chat`, без сервиса. Значение `Provider` в файлах чатов не
меняется, старые чаты открываются без миграции.

Для облачного чата клиент собирает тело `POST {server_url}/v1/chat`:
историю чата — в `messages`, параметры чата (`model`, `sampling`,
`reasoning`, `thinking`, `experts`, `response_format`) — в `settings`, и
добавляет `Authorization: Bearer <токен>`, если токен задан. Поле `api_key` в
теле не отправляется никогда: сервис отвечает на него `400`.

Ответ разбирается в `AgentReply`: `content` и `reasoning` — как есть,
`usage` и `timing` — в `MessageMeta` (`prompt_tokens`, `completion_tokens`,
`total_tokens`, `reasoning_tokens`, `duration_ms`, `sent_at`, `received_at`),
чтобы существующая строка телеметрии в TUI и в `agentcli ask` работала без
изменений. Поле `model` из ответа — фактически использованная сервисом
модель; показывать её, а не запрошенную.

Ошибки приходят конвертом `{"error": {"code", "message", "request_id"}}` и
должны превращаться в типизированный `AgentError`, а не в строку: `401` —
отсутствующий или неизвестный клиентский токен (с подсказкой про
`agentcli config set-token`), `400` — невалидный запрос, `422` — запрос
отклонён политикой сервиса, `429` — превышен лимит, `502` — ошибка
провайдера, `504` — провайдер не ответил, транспортная ошибка — сервис
недоступен по адресу `server_url`. `request_id` из ответа или из заголовка
`x-request-id` показывать в сообщении об ошибке: без него разбирательство по
логам сервиса невозможно.

Блок `policy` из ответа разбирать и сохранять в сообщении; отображать пока
только факт отклонения (код и причина стадии) в тексте ошибки.

## Конфигурация клиента

Поля `api_key` и `base_url` (адрес облачного провайдера) из конфига клиента
убрать. Вместо них:

- `server_url` — адрес сервиса `agentd`, по умолчанию `http://127.0.0.1:8080`;
- `client_token` — клиентский токен для `Authorization: Bearer`. Токен
  настраивает сам пользователь, он хранится в конфиге клиента и показывается
  маскированным (как раньше показывался ключ). Пустой токен допустим: сервис
  с пустым `AGENTD_CLIENT_TOKENS` аутентификацию не проверяет.

Команды: `config set-key` заменяется на `config set-token`, `config set-url`
задаёт адрес сервиса. `config show` печатает `server_url` и маскированный
токен и больше не упоминает ключ провайдера. `config models` берёт список
моделей из `GET {server_url}/v1/models`, а не из встроенного списка; при
недоступном сервисе — понятная ошибка, а не пустой список. Настройки Ollama
(`ollama models`, `ollama use`, `ollama set-url`) остаются как есть.

Старый конфиг с полями `api_key`/`base_url` читается без ошибки: неизвестные
поля игнорируются, а при их наличии клиент один раз печатает предупреждение,
что ключ провайдера больше не используется и его следует убрать из файла.
Сам файл при этом не переписывать молча.

В TUI раздел «Подключение» (`Ctrl+P`) для облачного чата содержит адрес
сервиса, токен и модель — вместо Base URL и ключа. Раздел для Ollama не
меняется. Адрес и токен сохраняются в глобальный конфиг по `Ctrl+S` и
применяются к следующим запросам без перезапуска, как сейчас.

## Что должно стать невозможным

- `agentcli` не собирается, если попытаться обратиться к облачному провайдеру
  напрямую: нужного типа в его графе зависимостей нет.
- В конфиге клиента нет места для ключа провайдера.
- Ни один запрос клиента не уходит на `api.deepseek.com` (и любой другой
  `base_url` провайдера) — только на `server_url` и на локальный Ollama.

## Изменения в репозитории `agent-sever`

Сервис переходит с `agentcore::agent::HttpAgent` на `agentupstream`. В
`Cargo.toml` добавляется вторая git-зависимость на тот же репозиторий, а
локальный `.cargo/config.toml` с секцией `[patch]` начинает подменять оба
крейта:

```toml
[patch."https://github.com/Egor-Liadsky/agent-cli"]
agentcore = { path = "../agent-cli/crates/core" }
agentupstream = { path = "../agent-cli/crates/upstream" }
```

Порядок остаётся прежним: сначала изменения ядра пушатся в `agent-cli/main`,
затем в `agent-sever` без `[patch]` выполняется `cargo generate-lockfile` и
`cargo test --locked`. Поведение сервиса и контракт `/v1` при этом не
меняются — это чистый перенос кода провайдера в отдельный крейт.

## Тесты

- `ServerAgent` против замоканного сервиса (`wiremock`): успешный ответ с
  разбором `usage`/`timing`; `401`, `422`, `429`, `502`, `504` дают
  соответствующие варианты `AgentError`; недоступный адрес даёт ошибку
  транспорта, а не панику.
- Тело запроса, собранное клиентом, не содержит поля `api_key` и содержит
  историю в `messages`.
- Заголовок `Authorization` отсутствует при пустом токене и присутствует при
  заданном.
- Чтение старого конфига с полями `api_key`/`base_url` не падает.
- Ollama-путь по-прежнему идёт мимо сервиса: запрос уходит на `ollama_url`.
- Тесты `agentcore` и `agent-sever`, существующие сейчас, остаются зелёными.

## Вне задачи

- Стриминг ответа.
- Хранение истории чатов на сервере: история по-прежнему живёт у клиента и
  целиком уходит в каждом запросе.
- Регистрация пользователей, выдача токенов, квоты.
- Изменение контракта `/v1` и логики конвейера на сервисе.

## Порядок работы

Проект использует OpenSpec (`openspec/`). Сначала оформи предложение изменения
(proposal, delta-спеки, задачи), дождись подтверждения, потом реализуй по
задачам. Каждый шаг завершать зелёной сборкой и тестами:

1. Новые крейты `agentupstream` и `agentclient`, перенос облачного кода из
   `agentcore` — без изменения поведения CLI (клиент временно продолжает
   работать как раньше, но уже через `agentupstream`).
2. `ServerAgent` в `agentclient` и его тесты против `wiremock`.
3. Переключение `agentcli` на `ServerAgent`, снятие зависимости на
   `agentupstream`, сохранение прямого пути в Ollama.
4. Конфигурация клиента: `server_url`, `client_token`, команды, TUI, чтение
   старого конфига.
5. Перевод `agent-sever` на `agentupstream` и обновление `[patch]`.
6. README обоих репозиториев: новая схема запуска (сначала `agentd`, потом
   клиент), таблицы команд и переменных, раздел про Ollama как исключение.

Комментарии и документация — на русском, как в существующих файлах;
сообщения коммитов — на английском в повелительном наклонении. Комментировать
причину решения, а не пересказывать строку. Новых зависимостей не добавлять
сверх необходимых.
