# Промпт: HTTP-агент на Rust поверх ядра agent-cli

## Роль и цель

Ты — Rust-инженер. Нужно превратить существующий CLI-проект `agent-cli`
(`/Users/egor_lyadskiy/ai/agent-cli`) в сервис: HTTP-агент, который принимает
промпт от клиента по HTTP, прогоняет его через конвейер обработки, вызывает
модель по API key и возвращает результат клиенту. CLI/TUI должен продолжать
работать без изменений в поведении.

Сервис в дальнейшем будет развёрнут на хостинге, поэтому конфигурация,
логирование и завершение процесса должны быть пригодны для контейнера.

## Что уже есть в репозитории (переиспользовать, не переписывать)

- `src/agent/mod.rs` — трейт `Agent { async fn ask(&self, history: &[Message],
  settings: &ChatSettings) -> Result<AgentReply> }`, типы `Message`, `Role`,
  `AgentReply`, `MessageMeta` (токены, длительность, тайминги).
- `src/agent/http.rs` — `HttpAgent`: OpenAI-совместимый вызов
  `POST {base_url}/chat/completions` через `reqwest`, сборка системного промпта,
  проброс `max_tokens`/`stop`/sampling/`thinking`, разбор `usage` и
  `reasoning_content`/`reasoning`, разбор ошибок API, JSONL-логи запросов
  и ответов.
- `src/agent/ollama.rs` — тот же трейт для локального Ollama.
- `src/config.rs` — `Config` (api_key, base_url, model, provider, ollama_*),
  `ChatSettings` (provider, model, `ResponseFormat`, `SamplingParams`,
  `ReasoningMode`, `ThinkingMode`, experts) и логика выбора модели.
- `src/tui.rs`, `src/cli.rs`, `src/chats.rs`, `src/main.rs` — интерфейс
  пользователя, к сервису отношения не имеют.

Ядро сервиса — это `agent` + `config`. Всё, что делает CLI, поверх них.

## Целевая структура

Преобразовать пакет в cargo workspace:

- `crates/core` — библиотека `agentcore`: сюда переезжают `agent/` и `config.rs`
  без изменения публичного поведения. Плюс новый модуль конвейера (см. ниже).
- `crates/cli` — существующий бинарник `agentcli` (TUI, CLI-команды, чаты),
  зависит от `agentcore`.
- `crates/server` — новый бинарник `agentd`: HTTP-сервис на `axum` + `tokio`,
  зависит от `agentcore`.

Переезд файлов делать механически: сначала workspace и перенос модулей с
зелёной сборкой и работающим CLI, только потом новая функциональность.

## HTTP API

Формат — JSON, версионированный префикс `/v1`.

`POST /v1/chat`

Запрос:

```json
{
  "prompt": "текст запроса",
  "messages": [{"role": "user", "content": "..."}],
  "settings": {
    "provider": "cloud",
    "model": "deepseek-chat",
    "sampling": {"temperature": 0.2, "top_p": 0.9},
    "reasoning": "step-by-step",
    "thinking": "auto",
    "response_format": {"description": "...", "max_length": 800}
  },
  "metadata": {"client_request_id": "..."}
}
```

- Ровно одно из `prompt` / `messages` обязательно; `prompt` — сахар для
  истории из одного пользовательского сообщения.
- `settings` необязателен и накладывается поверх серверных значений по
  умолчанию (те берутся из конфигурации сервиса, а не из `~/.config`).
- Клиент **никогда** не передаёт ключ провайдера модели: ключ принадлежит
  сервису. Поле `api_key` в запросе — ошибка 400, а не тихое игнорирование.

Ответ 200:

```json
{
  "request_id": "…",
  "content": "ответ модели",
  "reasoning": "…или null",
  "model": "фактически использованная модель",
  "usage": {"prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0,
            "reasoning_tokens": null},
  "timing": {"duration_ms": 0, "sent_at": 0, "received_at": 0},
  "policy": {"input": [], "output": [], "judge": null}
}
```

`usage`/`timing` заполняются из существующего `MessageMeta`. Блок `policy` —
результаты стадий конвейера; сейчас пустой, но поле присутствует в контракте
с первого дня, чтобы клиенты его уже разбирали.

Прочие эндпоинты:

- `GET /healthz` — процесс жив, без обращений к внешним сервисам.
- `GET /readyz` — конфигурация валидна (ключ задан, base_url разобран).
- `GET /v1/models` — список моделей, разрешённых конфигурацией сервиса.

Ошибки — единый конверт:

```json
{"error": {"code": "invalid_request", "message": "…", "request_id": "…"}}
```

Коды статусов: 400 — невалидный запрос; 401 — неверный или отсутствующий
клиентский токен; 413 — превышен лимит тела; 422 — запрос отклонён input-
политикой; 429 — сработал лимит сервиса либо провайдер вернул rate limit;
502 — провайдер вернул ошибку; 504 — таймаут провайдера. Сообщения ошибок
провайдера не проксировать дословно наружу: логировать целиком, клиенту
отдавать нормализованный текст без внутренних адресов и ключей.

## Конвейер обработки (главное требование)

Обработка запроса должна быть явным конвейером, а не кодом внутри
обработчика, потому что позже в него добавятся input policy, output policy и
LLM-judge.

```
запрос → нормализация → input policy → вызов модели → output policy → judge → ответ
```

В `agentcore` описать трейты примерно такого вида:

```rust
#[async_trait]
pub trait InputPolicy: Send + Sync {
    async fn check(&self, ctx: &RequestContext) -> Result<PolicyOutcome>;
}

#[async_trait]
pub trait OutputPolicy: Send + Sync {
    async fn check(&self, ctx: &RequestContext, reply: &AgentReply) -> Result<PolicyOutcome>;
}

#[async_trait]
pub trait Judge: Send + Sync {
    async fn judge(&self, ctx: &RequestContext, reply: &AgentReply) -> Result<JudgeVerdict>;
}
```

`PolicyOutcome` должен уметь выражать три исхода: пропустить, изменить
полезную нагрузку (например, отредактированный промпт или замаскированный
ответ), отклонить с причиной и кодом. `RequestContext` несёт `request_id`,
историю, `ChatSettings`, идентификатор клиента и накопленные результаты стадий.

Сейчас реализовать по одной тривиальной реализации на трейт (пропускающей всё)
плюс `Pipeline`, который принимает `Vec<Arc<dyn InputPolicy>>`,
`Vec<Arc<dyn OutputPolicy>>` и `Option<Arc<dyn Judge>>`. Judge вызывается за
отдельным вызовом модели через тот же трейт `Agent`, поэтому конвейер должен
получать агента через `Arc<dyn Agent>`, а не создавать его сам. Никакой
реальной логики политик не писать — цель в том, чтобы добавление политики
позже было новым файлом и одной строкой регистрации, без правки обработчика.

## Конфигурация

Сервис конфигурируется переменными окружения (12-factor, для хостинга), с
разумными значениями по умолчанию:

- `AGENTD_BIND` (по умолчанию `0.0.0.0:8080`; на хостингах читать также `PORT`)
- `AGENTD_AUTH_TOKENS` — список токенов клиентов через запятую; пусто —
  сервис стартует, но при непустом списке проверка `Authorization: Bearer`
  обязательна. Сравнение токенов — по постоянному времени.
- `AGENTD_UPSTREAM_BASE_URL`, `AGENTD_UPSTREAM_API_KEY`, `AGENTD_MODEL`,
  `AGENTD_PROVIDER`, `AGENTD_OLLAMA_URL`
- `AGENTD_ALLOWED_MODELS` — белый список моделей для `settings.model`
- `AGENTD_REQUEST_TIMEOUT_MS`, `AGENTD_MAX_BODY_BYTES`,
  `AGENTD_MAX_CONCURRENCY`
- `AGENTD_LOG_FORMAT` = `json` | `text`, `AGENTD_LOG_DIR`

Ключ провайдера читается только из окружения и никогда не попадает в логи и
ответы; для диагностики использовать уже существующее маскирование
(`Config::masked_api_key`). Сервис не должен читать пользовательский
`~/.config/agentcli/config.toml` — это состояние CLI, а не сервиса.

## Обязательные исправления при переносе ядра

- `logs_dir()` в `src/agent/http.rs` строит путь от `CARGO_MANIFEST_DIR`, что
  в контейнере указывает на несуществующую директорию сборки. Путь логов
  должен приходить из конфигурации, а запись в файл — быть отключаемой.
- Запись логов сейчас синхронная внутри асинхронного пути; в сервисе она не
  должна блокировать обработчик (вынести в неблокирующий writer).
- `reqwest::Client` создавать один раз и переиспользовать (он уже такой в
  `HttpAgent` — важно не создавать агента на каждый запрос, а хранить в
  состоянии приложения).
- Ошибка «API key не задан» сейчас предлагает команду CLI; для сервиса нужен
  собственный текст и падение на старте, а не на первом запросе.

## Нефункциональные требования

- Таймаут на вызов провайдера и общий таймаут запроса; graceful shutdown по
  SIGTERM/SIGINT с дожатием активных запросов.
- Ограничение размера тела и ограничение конкурентности (`tower` слои).
- Structured logging через `tracing` + `tracing-subscriber`, JSON в проде.
  На каждый запрос: `request_id`, клиент, модель, длительность, статус,
  токены. Промпты и ответы в логи по умолчанию не писать — отдельный флаг.
- `request_id` генерируется на входе, возвращается в теле и в заголовке
  `x-request-id`, прокидывается во все стадии конвейера.
- Сервис без состояния: история приходит от клиента. Хранение сессий на
  сервере — вне текущей задачи.

## Тесты

- Юнит-тесты конвейера: политика пропускает, политика отклоняет (422),
  политика меняет промпт, judge возвращает вердикт — с фиктивной реализацией
  `Agent`, без сети.
- Тесты сериализации контракта: запрос с `prompt`, запрос с `messages`,
  запрос с обоими (ошибка), неизвестная модель (400), запрос с `api_key`
  (400).
- Интеграционные тесты HTTP через `axum::Router` в памяти: `/healthz`,
  успешный `/v1/chat` с замоканным провайдером (`wiremock`), 401 без токена,
  502 при ошибке провайдера, 504 при таймауте.
- Существующее поведение CLI не должно сломаться: `cargo build` и ручная
  проверка `agentcli ask` и `agentcli chat`.

Многостадийный `Dockerfile` (сборка на образе Rust, рантайм на

## Вне задачи (не делать сейчас)

- Стриминг ответа (SSE/WebSocket) — только не закрывать себе путь к нему в
  контракте и в трейтах.
- Реальные правила input/output политик и промпты judge.
- Многопользовательность, тарификация, квоты, хранение диалогов на сервере.
- Веб-интерфейс.

## Порядок работы

Проект использует OpenSpec (`openspec/`). Сначала оформи предложение
изменения (proposal + delta-спеки + задачи), дождись подтверждения, потом
реализуй по задачам. Каждый шаг завершать зелёной сборкой и тестами:
1) workspace и перенос ядра; 2) скелет сервиса и `/healthz`; 3) `/v1/chat`
поверх `Agent`; 4) конвейер и no-op стадии; 5) конфигурация, лимиты, логи;
6) тесты; 7) Dockerfile и README.

Комментарии в коде — на русском, как в существующих файлах. Не менять
публичное поведение CLI. Не добавлять зависимости сверх нужных: `axum`,
`tower`/`tower-http`, `tracing`, `tracing-subscriber`, и для тестов
`wiremock`.
