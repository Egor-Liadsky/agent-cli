# agent-cli

Консольный клиент на Rust для диалога с AI-агентом: облачным — через HTTP-сервис
[`agentd`](https://github.com/Egor-Liadsky/agent-sever), которому принадлежит
ключ провайдера, либо локальным — через [Ollama](https://ollama.com) на своей
машине.
Поддерживает разовые вопросы, интерактивный TUI-чат с историей на несколько
сессий и рендеринг ответов агента как Markdown прямо в терминале. Чаты
хранит сервис `agentd`: локальных файлов с историей у клиента нет.

## Архитектура

Проект собран как cargo workspace из четырёх крейтов:

| Крейт             | Каталог           | Кто зависит                    |
|-------------------|-------------------|--------------------------------|
| `agentcore`       | `crates/core`     | все остальные                  |
| `agentupstream`   | `crates/upstream` | только сервис `agentd`         |
| `agentclient`     | `crates/client`   | только `agentcli`              |
| `agentcli`        | `crates/cli`      | —                              |

Облачный провайдер вынесен в отдельный крейт `agentupstream` намеренно:
консольный клиент от него не зависит, поэтому прямой запрос к облачному API
из клиента невозможен — нужного типа нет в его графе зависимостей. Проверка:

```bash
cargo tree -p agentcli | grep agentupstream   # пусто
```

Локальный Ollama — единственное исключение: он остаётся в ядре и вызывается с
машины пользователя напрямую, потому что запросы туда никуда не уходят и ключа
не требуют.

**`crates/core` — библиотека `agentcore`:**

- **`config.rs`** — конфигурация (`provider`, `server_url`, `client_token`,
  `model`, `ollama_url`, `ollama_model`),
  хранится в TOML-файле в стандартной директории конфигов ОС
  (`~/.config/agentcli/config.toml` на Linux/macOS). Параметры агента
  (`ChatSettings`: модель, режим ответа, `response_format`, `sampling`, `reasoning`) в конфиге
  задают лишь значения по умолчанию для новых чатов — рабочие значения живут
  в самом чате.
- **`agent/`** — слой обращения к AI-агенту:
  - `mod.rs` — трейт `Agent`
    (`async fn ask(&self, history: &[Message], settings: &ChatSettings) -> Result<AgentReply>`)
    и общие типы `Message`/`Role`/`MessageMeta`, что позволяет позже добавить
    другие реализации агента без изменения остального кода. `Role` — `User`,
    `Assistant` и `System` (конструктор `Message::system`): служебные данные
    (например, системное сообщение сервиса `agentd`) передаются этой ролью, а
    не текстовым маркером внутри сообщения пользователя;
  - `error.rs` — типизированная `AgentError` (`Timeout`, `Provider`,
    `Transport`, `MissingApiKey`, `Decode`, `Unauthorized`, `InvalidRequest`,
    `PolicyRejected`, `RateLimited`). Она кладётся внутрь `anyhow::Error`,
    поэтому вызывающая сторона отличает таймаут от отказа политики через
    `downcast_ref`, а не по тексту сообщения; идентификатор запроса сервиса
    (`request_id`) хранится в самой ошибке и печатается в её тексте;
  - `local.rs` — `OllamaAgent`: реализация `Agent` для локальных моделей;
  - `ollama.rs` — локальные модели: нативный API Ollama
    (`POST {ollama_url}/api/chat`, `GET {ollama_url}/api/tags`). Нативный, а не
    OpenAI-совместимый слой, потому что он отдаёт цепочку рассуждения
    (`message.thinking`), счётчики токенов и `top_k` — всё, что приложение уже
    показывает для облачных моделей.
- **`logging.rs`** — журнал обмена (`ExchangeLog`) в формате JSON Lines. Директорию задаёт вызывающая сторона, запись можно полностью
  выключить, а строки уходят в фоновый поток, поэтому диск не задерживает
  ответ модели. Кроме файлов есть `ExchangeLog::to_sink`: записи отдаются
  приёмнику `ExchangeSink` вызывающей стороны — так сервис `agentd` выводит
  обмен с провайдером в свой журнал, не создавая файлов в контейнере.

**`crates/upstream` — библиотека `agentupstream`:**

- `UpstreamAgent` — реализация `Agent` поверх OpenAI-совместимого
  `POST {base_url}/chat/completions`: тело запроса, ключ провайдера, разбор
  `usage` и `reasoning_content`. Единственный потребитель — сервис `agentd`.

**`crates/client` — библиотека `agentclient`:**

- `ServerAgent` — реализация `Agent` поверх контракта сервиса
  (`POST {server_url}/v1/chat`): история уходит в `messages`, параметры чата —
  в `settings`, токен — в заголовке `Authorization: Bearer`. Поле `api_key` в
  теле не отправляется никогда: сервис отвечает на него `400`. Метод
  `ask_in_chat` шлёт запрос с `chat_id` и только новой репликой: историю
  сервис берёт из чата сам и сам записывает обмен.
- `ChatsClient` — чаты сервиса: список (`GET /v1/chats`), история
  (`GET /v1/chats/{id}`), создание, изменение и удаление чата, а также
  дозапись готового обмена (`POST /v1/chats/{id}/messages`). Страницы списка
  и сообщений дочитываются до конца, ошибки приходят той же типизированной
  `AgentError`, что у `ServerAgent`.
- `list_models` — список моделей сервиса (`GET {server_url}/v1/models`).

**`crates/cli` — бинарник `agentcli`:**

- **`agent.rs`** — выбор агента по провайдеру чата: `cloud` — `ServerAgent`,
  `ollama` — `OllamaAgent`. Облачного провайдера в этом наборе нет.

- **`main.rs`** — точка входа: разбирает CLI-команды и вызывает
  соответствующий обработчик (`ask`, `chat`, `config`, `ollama`).
- **`cli.rs`** — описание команд и аргументов на `clap` (`derive`-API).
- **`logging.rs`** — где консольный клиент держит журнал обмена и какую
  подсказку про клиентский токен он подставляет в сообщение об ошибке.
- **`chats.rs`** — чат в памяти клиента (`ChatSession`) и его представление:
  заголовок из первой реплики, блок переноса контекста, метка времени. Своего
  хранилища у клиента нет — список, история и параметры чата приходят от
  сервиса.
- **`tui.rs`** — интерактивный интерфейс чата на `ratatui` + `crossterm`:
  боковая панель со списком чатов, окно истории сообщений с прокруткой,
  поле ввода, асинхронная отправка запросов к агенту (через `tokio::spawn`
  и `mpsc`-канал) со спиннером ожидания. Список чатов и история приходят от
  сервиса теми же фоновыми задачами, поэтому пустой и незагруженный список —
  штатные состояния экрана.
- **`markdown.rs`** — единая настройка стилей Markdown-рендера
  (`termimad`), используется как при печати одиночного ответа, так и
  внутри истории TUI (через `ansi-to-tui`, конвертирующий ANSI-разметку
  `termimad` в виджеты `ratatui`).

### Журнал обмена

Запросы и ответы пишутся в `requests.jsonl` и `responses.jsonl`. Для облачных
чатов это обмен с сервисом `agentd`, а не с провайдером: обмен с провайдером
журналирует сам сервис. Консольный
клиент кладёт их в пользовательскую директорию данных ОС —
`~/Library/Application Support/agentcli/logs` на macOS,
`~/.local/share/agentcli/logs` на Linux. Переменная окружения
`AGENTCLI_LOG_DIR` задаёт свою директорию:

```bash
AGENTCLI_LOG_DIR=/tmp/agentcli-logs cargo run -p agentcli -- ask "привет"
```

### Поток данных

1. Пользователь вводит команду (`ask`/`chat`) или сообщение в TUI.
2. `Config::load()` читает адрес сервиса, клиентский токен и модель из конфига.
3. `CliAgent` смотрит на провайдера чата: для облака `ServerAgent` шлёт
   `POST {server_url}/v1/chat` с историей и параметрами чата, для Ollama —
   `OllamaAgent` шлёт `POST {ollama_url}/api/chat` напрямую, мимо сервиса.
4. Ответ разбирается (`serde_json`): `usage` и `timing` попадают в телеметрию
   сообщения, `model` — фактически использованная сервисом модель. При ошибке
   конверт `{"error": {...}}` превращается в `AgentError` вместе с
   `request_id`, по которому запрос ищется в журнале сервиса.
5. Текст ответа рендерится как Markdown (`termimad`) и выводится в
   терминал либо добавляется в историю чата. Обмен облачного чата записал сам
   сервис (запрос шёл с `chat_id`), обмен с локальной моделью клиент
   дозаписывает запросом `POST /v1/chats/{id}/messages` — вопрос и ответ одним
   вызовом.

## Инструменты и зависимости

| Назначение                     | Крейт                          |
|---------------------------------|---------------------------------|
| CLI-аргументы                  | `clap` (derive)                 |
| Асинхронный рантайм             | `tokio`                         |
| HTTP-клиент                     | `reqwest` (json, rustls-tls)     |
| Сериализация                    | `serde`, `serde_json`, `toml`   |
| Обработка ошибок                | `anyhow`                        |
| Пути к конфигам ОС              | `dirs`                          |
| Трейты с async-методами         | `async-trait`                   |
| TUI                              | `ratatui`, `crossterm`, `futures` |
| Рендер Markdown в терминале      | `termimad`, `ansi-to-tui`        |
| Индикация прогресса/стиль текста | `indicatif`, `console`          |

Терминальные зависимости (`clap`, `ratatui`, `crossterm`, `termimad`,
`ansi-to-tui`, `indicatif`, `console`, `arboard`) живут только в `agentcli`:
`agentcore` от терминала не зависит.

## Запуск

Требуется установленный Rust (издание 2024, см. `Cargo.toml`).

Сборка:

```bash
cargo build --release
```

Сначала запускается сервис, потом клиент: облачная модель доступна клиенту
только через `agentd`, и ключ провайдера хранит сервис, а не клиент.

```bash
# в репозитории agent-sever
AGENTD_UPSTREAM_API_KEY=sk-... PORT=8080 cargo run --release
```

Адрес сервиса и клиентский токен:

```bash
cargo run -p agentcli -- config set-url http://127.0.0.1:8080
cargo run -p agentcli -- config set-token <ВАШ_ТОКЕН>
```

Токен нужен, только если сервис запущен с непустым `AGENTD_CLIENT_TOKENS`; при
пустом списке сервис аутентификацию не проверяет, и заголовок `Authorization`
клиент не отправляет. Токен можно ввести и не выходя из чата: `Ctrl+P`, раздел
«Подключение» (см. [Модель, сервис и токен](#модель-сервис-и-токен)).

Модель по умолчанию и список моделей сервиса:

```bash
cargo run -p agentcli -- config set-model deepseek-chat
cargo run -p agentcli -- config models   # GET {server_url}/v1/models
```

`config models` спрашивает список у сервиса: встроенного списка у клиента нет,
и при недоступном сервисе команда завершается ошибкой с его адресом. В TUI
поведение мягче: при старте и по `Ctrl+L` список тоже запрашивается у сервиса,
но при его недоступности чат не падает, а остаётся на встроенном/конфигурном
списке (см. [Модель, сервис и токен](#модель-сервис-и-токен)).

Лимит контекста по умолчанию для НОВЫХ чатов (см.
[Модель, сервис и токен](#модель-сервис-и-токен)):

```bash
cargo run -p agentcli -- config context-limit set 4000   # сохранить умолчание
cargo run -p agentcli -- config context-limit clear       # снять умолчание
cargo run -p agentcli -- config context-limit show        # показать текущее умолчание
```

`set` отклоняет `0` и нечисловые значения, не изменяя сохранённое значение.
Значение копируется в `max_context_tokens` только НОВЫХ чатов при создании;
уже открытые чаты команда не трогает — их лимит меняется в TUI (`Ctrl+P`).
У чата с заданным лимитом каждый `POST /v1/chat` уходит с полем
`settings.max_context_tokens`:

Умолчания компактизации истории (сервис `agentd`) для НОВЫХ чатов — тем же
образом:

```bash
cargo run -p agentcli -- config summary set true --keep-messages 20 --step-messages 10
cargo run -p agentcli -- config summary clear   # снять все умолчания
cargo run -p agentcli -- config summary show    # показать текущие умолчания
```

`set` принимает `enabled` (`true`/`false`, `on`/`off`, `yes`/`no`) и/или
`--keep-messages`/`--step-messages`; хотя бы одно значение обязательно, `0`
в числовых полях отклоняется. Как и `context-limit`, эти умолчания
копируются в настройки только НОВОГО чата при создании — уже открытые чаты
меняются в TUI (`Ctrl+P`).

```json
{
  "prompt": "...",
  "settings": {
    "provider": "cloud",
    "max_context_tokens": 4000
  }
}
```

По умолчанию используется `server_url = http://127.0.0.1:8080` и
`model = deepseek-v4-flash`. Конфиг лежит в
`~/.config/agentcli/config.toml` (на macOS —
`~/Library/Application Support/agentcli/config.toml`) и создаётся
автоматически. Свой список моделей для быстрого выбора задаётся в нём полем
`models` (массив строк) — если он пуст, используется встроенный список.

Конфиг прежней схемы с полями `api_key` и `base_url` читается без ошибки:
клиент один раз печатает предупреждение, что ключ провайдера больше не
используется, и файл не переписывает — убрать эти поля решает пользователь.

Посмотреть текущую конфигурацию (токен маскируется):

```bash
cargo run -p agentcli -- config show
```

Задать один вопрос и получить ответ:

```bash
cargo run -p agentcli -- ask "Как настроить логирование в Rust?"
```

Запустить интерактивный чат (TUI):

```bash
cargo run -p agentcli -- chat
```

Управление в TUI:

- `Enter` — отправить сообщение / выбрать чат в боковой панели;
- `Tab` — переключиться между полем ввода и списком чатов;
- `Ctrl+N` — создать новый чат (создаёт его сервис, идентификатор приходит
  от него);
- `Ctrl+E` — перезагрузить список чатов у сервиса;
- `Ctrl+U` — повторить запись обмена, которую сервис не принял;
- `d` в списке чатов — удалить выбранный чат (`y`/`Enter` — подтвердить,
  `n`/`Esc` — отмена);
- `Ctrl+O` — импорт контекста других чатов в текущий (`↑`/`↓` — выбор,
  `Space` — отметить, `Enter` — перенести, `Esc` — отмена);
- `Ctrl+P` — параметры текущего чата (подключение, контекст, режим ответа,
  стратегия рассуждения, формат, сэмплирование), `Ctrl+S` — сохранить,
  `Esc` — отмена;
- `Ctrl+F` — факты текущего чата (стратегия `facts`): `↑`/`↓` — выбор,
  `Enter` — править значение, `n` — новый факт, `d` — удалить, `Esc` —
  закрыть;
- `Ctrl+B` — ветки текущего чата (стратегия `branching`): `↑`/`↓` — выбор,
  `Enter` — переключить активную, `n` — новая ветка от выбранного сообщения,
  `Esc` — закрыть;
- `Ctrl+R` — показать/скрыть цепочку рассуждений модели в истории;
- `↑`/`↓`, `PageUp`/`PageDown` — прокрутка истории;
- `Ctrl+Y` — скопировать текст из поля ввода в системный буфер обмена; по
  ssh, где нативного буфера нет, текст уходит в буфер локальной машины
  через OSC 52;
- TUI не захватывает события мыши (`EnableMouseCapture` намеренно не
  включаем), поэтому нативное выделение текста мышью для копирования в OS
  работает как обычно; прокрутка колесом мыши недоступна — используйте
  `↑`/`↓`, `PageUp`/`PageDown`;
- обычная вставка (`Cmd+V` / `Ctrl+Shift+V`) вставляет текст в поле ввода
  целиком, переносы строк схлопываются в пробелы;
- `Esc` / `Ctrl+C` — выход.

### Модель, сервис и токен

Окно параметров чата (`Ctrl+P`) — слева список из пяти разделов
(Подключение, Контекст, Формат ответа, Рассуждение, Сэмплинг), справа поля
активного раздела: под значением каждого поля всегда видна короткая
подсказка о его смысле; под списком полей — панель «Пояснение» с более
развёрнутым описанием выделенного поля (или раздела, пока курсор ещё в
списке слева).

Раздел «Подключение» в параметрах чата (`Ctrl+P`) содержит такие поля:

- **Модель** — модель именно этого чата. `◀`/`▶` перебирают модели, разрешённые
  сервисом (`GET /v1/models`): список подгружается фоном при старте TUI и
  обновляется по `Ctrl+L`, пока открыт провайдер «Облачный API»; если сервис
  недоступен, используется встроенный/конфигурный список (поле `models` в
  конфиге, иначе список по умолчанию). Ввод с клавиатуры задаёт любое другое
  имя, `Ctrl+D` очищает поле — тогда используется модель по умолчанию из
  конфига. Разные чаты могут работать на разных моделях; выбранная модель
  показана в заголовке панели чата.
- **Адрес сервиса agentd** — общий для всех чатов.
- **Токен сервиса** — клиентский токен, общий для всех чатов; на экране
  показаны только последние 4 символа. Токен удобнее вставить из буфера обмена
  (`Cmd+V` / `Ctrl+Shift+V`), чем набирать.

Раздел «Контекст» в параметрах чата (`Ctrl+P`) содержит такие поля:

- **Стратегия контекста** — как сервис `agentd` собирает историю чата для
  запроса модели: `◀`/`▶` перебирают «Умолчание сервиса»,
  «Пересказ» (`summary` — старые сообщения заменяются кратким пересказом,
  прежнее поведение), «Окно последних сообщений» (`sliding_window` — старые
  сообщения просто отбрасываются, без замены), «Устойчивые факты» (`facts` —
  ключевые данные диалога хранятся отдельно и уходят вместе с хвостом
  истории; экран `Ctrl+F`) и «Ветвление диалога» (`branching` — история
  собирается по цепочке активной ветки; экран `Ctrl+B`). «Умолчание сервиса»
  — стратегию определяет переменная `AGENTD_CONTEXT_STRATEGY`. Значение
  принадлежит конкретному чату, разовое переопределение на один запрос в TUI
  не предусмотрено (доступно через контракт `/v1` для интеграций).
- **Окно последних сообщений** — размер окна для стратегий
  «Окно последних сообщений» и «Устойчивые факты»; пусто — операторское
  умолчание сервиса (`AGENTD_CONTEXT_WINDOW_MESSAGES`).
- **Лимит контекста (токены, настройка этого чата)** — необязательный
  клиентский лимит контекстного окна: сужает операторский лимит сервиса
  `agentd` для каждого запроса этого чата (поле `settings.max_context_tokens`
  в `POST /v1/chat`). Пустое поле — лимит не задан, запросы уходят без этого
  поля, действует операторский лимит сервиса по умолчанию. Значение
  принадлежит конкретному чату — как модель: у разных чатов могут быть разные
  лимиты, изменение одного не затрагивает другие. Непустой ввод, не
  являющийся положительным целым числом, отклоняется с сообщением об ошибке,
  а прежнее сохранённое значение остаётся без изменений. Клиент сам значение
  не проверяет — превышение операторского лимита или истории чата отклоняет
  сервис (`400 context_limit_invalid` / `400 context_limit_exceeded`), и
  клиент показывает это как обычную ошибку запроса. Умолчание для НОВЫХ чатов
  задаётся командой `agentcli config context-limit`.
- **Компактизация истории** и связанные с ней **дословный хвост** и **шаг
  пересказа** — необязательные настройки этого чата, действующие поверх
  операторских умолчаний сервиса `agentd`: включают или выключают замену
  вытесненной части истории кратким пересказом, задают потолок сообщений,
  уходящих провайдеру дословно, и шаг, с которым пересказ перестраивается.
  Как и лимит контекста, поля принадлежат конкретному чату, пустое поле
  оставляет операторское умолчание сервиса, а непустой нечисловой или нулевой
  ввод отклоняется без изменения сохранённого значения. Выход за операторские
  границы отклоняет сервис (`400 summary_settings_invalid`). Умолчания для
  НОВЫХ чатов задаются командой `agentcli config summary`.

Адрес и токен — общие для всех чатов, сохраняются в глобальный конфиг по
`Ctrl+S`. Модель, лимит контекста и настройки компактизации — параметры
именно этого чата, по `Ctrl+S` сохраняются в его настройки на сервисе
(`PATCH /v1/chats/{id}`); другие чаты не меняются. Во всех случаях
последующие запросы уходят уже с новыми значениями — перезапуск не нужен.
Модель и остальные параметры чата уходят в сервис запросом
`PATCH /v1/chats/{id}` и применяются локально после его подтверждения.

### Где хранятся чаты

Чаты хранит сервис `agentd`: список, история сообщений и параметры каждого
чата живут в его базе, а клиент только показывает их. Файлов с историей на
машине пользователя нет — в каталоге конфигурации остаются лишь сам
`config.toml` и журналы обмена.

Так устроены чаты обоих провайдеров. Облачный ответ даёт сервис и сам
записывает обмен, а ответ локальной модели Ollama приходит мимо сервиса,
поэтому вопрос и ответ клиент дозаписывает в чат одним запросом. Если
дозапись не удалась, ответ остаётся на экране, чат помечен как несохранённый
с причиной и `request_id`, а `Ctrl+U` повторяет попытку; при выходе из
клиента такой обмен теряется.

Один и тот же чат виден с любой машины, подключённой к тому же сервису с тем
же клиентским токеном: владельцем чата сервис считает отпечаток токена.
Поэтому смена токена меняет и список чатов — прежние остаются у прежнего
владельца.

### Работа без сервиса

Без сервиса TUI всё равно открывается: список чатов пуст, а на месте панели
чата видна причина с адресом сервиса и `request_id`, если сервис его вернул.
`Ctrl+E` повторяет загрузку — когда сервис поднялся, список заполняется без
перезапуска клиента. Пока список не загружен, создать чат и отправить
сообщение нельзя: обмену негде записаться. При отказе `401` в причине есть
подсказка задать клиентский токен (`agentcli config set-token <TOKEN>`).

Это касается и чатов с локальной моделью: сам ответ Ollama даёт на машине
пользователя, но чат и его история принадлежат сервису.

### Локальные модели через Ollama

Чат может отвечать локальной моделью — запросы никуда не уходят с машины, не
идут через сервис `agentd` и ключа не требуют. Нужен запущенный Ollama (`ollama serve`) и хотя бы одна
скачанная модель (`ollama pull gemma3:12b`).

В TUI: `Ctrl+P` → раздел «Подключение» → поле **Провайдер** (`◀`/`▶` или
пробел) переключает чат между «Облачный API» и «Ollama (локально)». Для
Ollama вместо адреса сервиса и токена показывается поле «Адрес Ollama», а `◀`/`▶` в
поле «Модель» перебирают локально скачанные модели. Список подгружается при
старте, `Ctrl+L` обновляет его (например, после `ollama pull`) — та же
клавиша, что обновляет облачный список: она смотрит на текущий провайдер
чата и обновляет список именно того. Провайдер
хранится в самом чате, поэтому облачные и локальные чаты спокойно живут рядом
и открываются в соседних панелях.

Из командной строки:

```bash
agentcli ollama models
```

```bash
agentcli ollama use gemma3:12b
```

```bash
agentcli ollama set-url http://192.168.1.10:11434
```

`ollama models` показывает скачанные модели (точкой отмечена выбранная),
`ollama use` делает модель и провайдера `ollama` значениями по умолчанию для
новых чатов, `ollama set-url` меняет адрес сервера (по умолчанию
`http://localhost:11434`). Вернуть облако по умолчанию:

```bash
agentcli config set-provider cloud
```

Запросы к Ollama идут в обход сервиса `agentd` и в обход HTTP-прокси из
окружения (`HTTP_PROXY`, `HTTPS_PROXY`): сервер работает на самой машине, а прокси обрывает долгие
ответы больших моделей по своему таймауту — это возвращается как `502` с
пустым телом. Облачных запросов это не касается, они по-прежнему уважают
настройки прокси.

Ограничения локального режима: `stop`, `max_length`, `temperature`, `top_p`,
`top_k`, `frequency_penalty`, `presence_penalty` и режим thinking передаются в
`options`/`think` нативного API; токены рассуждения отдельной строкой Ollama не
считает, поэтому в телеметрии видны только токены запроса, ответа и скорость.
Режим thinking `on` для модели без поддержки размышления Ollama вернёт ошибкой
— оставьте `auto`.

### Режим thinking

У моделей с встроенным размышлением его можно выключить — в параметрах чата
(`Ctrl+P`, раздел «Рассуждение», поле «Режим thinking у модели») или глобально
для новых чатов:

```bash
agentcli config reasoning --thinking off
```

Значения: `auto` (по умолчанию — поле не отправляется, решает API), `on`,
`off`. В запрос уходит `thinking: {"type": "enabled" | "disabled"}`, а для
Ollama — нативное поле `think: true | false`; в режиме
`auto` поле не отправляется вовсе, чтобы не ломать провайдеров, которые его не
поддерживают. С выключенным thinking ответ приходит без цепочки рассуждений и
без токенов на неё — заметно дешевле и быстрее.

### Рассуждение и телеметрия ответа

Если модель возвращает цепочку рассуждений (поле `reasoning_content` у
DeepSeek, `reasoning` у OpenAI-совместимых прокси, `message.thinking` у
Ollama), она показывается в
истории отдельным блоком над ответом. `Ctrl+R` скрывает и снова показывает
этот блок; он же сохраняется в файле чата вместе с сообщением.

Рядом с заголовком каждого ответа выводится строка телеметрии: фактическая
модель ответа (её сообщает сервис — она может отличаться от запрошенной), время
получения, длительность запроса, число токенов запроса (`↑`) и ответа (`↓`),
токены рассуждения (если API их отделяет) и скорость генерации в токенах в
секунду. Пока агент отвечает, под историей идёт счётчик прошедшего времени.
Команда `agentcli ask` печатает ту же сводку одной строкой после ответа.

### Роль `system` в истории

История чата может содержать сообщение роли `system` — например, первым
сообщением ответа сервиса `agentd` при работе через него (базовый текст
сервиса плюс служебные разделы действующей стратегии контекста, см. README
`agent-sever`). В истории чата оно показывается отдельным блоком, как и
сообщения ролей `user`/`assistant`.

На проводе системное сообщение всегда одно: оба провайдера
(`agentupstream` — облачный Chat Completions, `agent/ollama.rs` — нативный
API Ollama) склеивают текст `system_prompt(settings)` (стратегия
рассуждения, формат ответа) с системным сообщением истории, если оно есть,
в одно сообщение `role: "system"` первым в запросе. Раздельно эти два
источника никогда не уходят: часть моделей учитывает только первое
системное сообщение.

### Стратегия рассуждения

В параметрах чата (`Ctrl+P`, поле «Стратегия рассуждения», переключается
`◀`/`▶` или пробелом) выбирается, как агент подходит к задаче:

- **По умолчанию** — без дополнительных инструкций;
- **Решать пошагово** — разбор задачи на пронумерованные шаги и итог;
- **Составить промпт для решения** — агент сначала формулирует подробный
  промпт задачи, затем решает по нему;
- **Группа экспертов** — заданные эксперты разбирают задачу и дают
  согласованный ответ.

Состав группы задаётся в том же окне полем «Эксперты» — список ролей через
запятую, например `аналитик, инженер по данным, критик`. Роль можно описать
подробнее прямо в строке: `безопасник (ищет риски утечек)`. Пустое поле —
состав по умолчанию: аналитик, инженер, критик.

Стратегия хранится в файле чата, для новых чатов значение по умолчанию
задаётся глобально:

```bash
cargo run -p agentcli -- config reasoning step-by-step
```

```bash
cargo run -p agentcli -- config reasoning expert-panel --experts "аналитик, инженер, критик"
```

Допустимые значения: `default`, `step-by-step`, `prompt-craft`,
`expert-panel`. Без аргументов команда показывает текущую стратегию и состав
группы; `--experts ""` возвращает состав по умолчанию.

### Импорт контекста других чатов

`Ctrl+O` открывает окно со списком остальных чатов, у которых есть история.
Отмеченные чаты переносятся в текущий одним сообщением: заголовок
`[Контекст из чата «...»]` и вся переписка построчно (`Вы:` / `Агент:`).
Исходные чаты не меняются, сообщение видно в истории и уходит агенту вместе
со следующим запросом. Название чата от импорта не меняется.

Контекст строится по истории, полученной от сервиса, поэтому чат-источник,
история которого ещё не загружена, перенести нельзя: клиент запрашивает её и
сообщает, что перенос не выполнен.

После установки релизного бинарника можно использовать напрямую:

```bash
./target/release/agentcli ask "..."
```

### Факты и ветки чата (стратегии `facts` и `branching`)

Стратегия `facts` хранит ключевые данные диалога как пары «ключ-значение»
отдельно от сообщений и обновляет их автоматически после каждого сообщения
пользователя. Экран `Ctrl+F` показывает список фактов действующего чата,
`Enter` открывает правку значения существующего ключа, `n` — создание новой
пары, `d` — удаление выбранного ключа. Правка отправляется сразу
(`PUT`/`DELETE /v1/chats/{id}/facts/...`), без отдельного подтверждения.

Стратегия `branching` даёт чату несколько независимых продолжений от общей
точки. Экран `Ctrl+B` показывает список веток с активной; `n` открывает
список сообщений чата для выбора точки ветвления (`↑`/`↓`, `Enter` —
подтвердить), затем поле имени новой ветки. `Enter` на ветке в списке
переключает её активной — окно чата после этого показывает историю именно
этой ветки.

Без TUI — те же операции подкомандами `agentcli` по идентификатору
существующего чата:

```bash
cargo run -p agentcli -- facts <CHAT_ID> list
cargo run -p agentcli -- facts <CHAT_ID> set budget "не больше 250000"
cargo run -p agentcli -- facts <CHAT_ID> delete budget

cargo run -p agentcli -- branches <CHAT_ID> list
cargo run -p agentcli -- branches <CHAT_ID> create 12 "альтернативный вариант"
cargo run -p agentcli -- branches <CHAT_ID> activate <BRANCH_ID>
```

`from_seq` в `branches create` — порядковый номер сообщения активной ветки,
с которого начинается новая ветка; проще всего увидеть нужный номер в экране
`Ctrl+B` → `n` в TUI (список сообщений чата с номерами) и оттуда же создать
ветку, если под рукой есть интерактивный клиент.
